# Effect validation facade — issue #19

Bundle `0.1.0-preview.9` adds `src/validation.ts`, re-exported from the authoring package entrypoint. It adapts the existing synchronous reference validators using installed Effect 4 `Effect.try`, `Data.TaggedError` and `Brand`; no new dependency, service, Layer, I/O or asynchronous runtime is introduced. Raw wire schemas and synchronous entrypoints retain their behavior and types.

`decodeOperationEffect(input)` returns `Effect<ValidatedOperation, ReferenceValidationError, never>`. Success means strict structure and the existing tenant/job correlation checks passed. It does not establish a valid operation-ID commitment, deadline freshness, authenticated identity, lease, fencing, selection or authorization. Scalar wire fields remain strings; the aggregate result carries the validated-phase brand.

`decodeCanonicalEffect(kind, bytes, version)` requires explicit version `"1"` or `"2"`. Supported kind/version pairs are restricted by declarations: v1 supports all existing canonical kinds and signature envelopes; v2 supports plan, manifest and signature. Success returns `ValidatedCanonical<Version, Kind>` with the corresponding schema fields plus a kind/version brand, after the existing size/depth, fatal UTF-8, JSON, strict schema, reference semantic and exact canonical-byte checks. Signatures are structurally checked, not cryptographically verified; commitments, cross-object consistency, trust/allowlists and authenticated approval are separate gates. Unsupported pairs from untyped JavaScript fail validation.

Both facades are lazy and revalidate on every execution. Inputs must remain caller-owned and stable until execution; no immutable input snapshot is captured when constructing an Effect. Successful values describe validation at that execution, not permanent trust. Brand constructors are private to the facade and applied only after the full reference validator. Brands are compile-time phase markers, not security boundaries against explicit casts, deliberate nominal-brand construction or later mutation through JavaScript/aliases; do not mutate validated results or treat brands as authorization.

`ReferenceValidationError` has tag `ReferenceValidationError`, code `INVALID_OPERATION` or `INVALID_CANONICAL`, and fixed message `Reference validation failed`. Codes identify the API, not individual fields/phases. The adapter intentionally maps every synchronous exception from its reference-validation call to this coarse typed failure, including unexpected throws; debugging detail is lost. It retains no input, original cause or parser/schema message. Callers can handle failures with `Effect.result`, `Effect.flip` or tag-based handling. Defects introduced outside the wrapped call are not sanitized by this facade.

The synchronous `decodeOperation`, `canonicalBytes` and `decodeCanonical` compatibility APIs still throw; JSON parser diagnostics can include input. Do not send those diagnostics to logs or outward responses without a separate safe boundary. No logging is added here.

`tests/validation.test.mjs` exercises typed failures through `Effect.result`/`Effect.flip`, synthetic `TOKEN_X` exclusion from message/string/JSON/stack, semantic checks, all v1/v2 golden objects/envelopes, negative bytes and lazy execution. `type-tests/validation.ts` compiles against emitted public declarations and rejects structural substitutes, wrong kinds/versions and omitted format selection. Run `pnpm build`, `pnpm test:types` and `node --test tests/validation.test.mjs` for focused checks; `pnpm check` includes the declaration and runtime gates. Existing canonical tests retain wire/digest/signature evidence. This enables no assurance profile or runtime authorization.
